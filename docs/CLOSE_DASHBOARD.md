# Close Dashboard API surface

`bitwave close` exposes the organization endpoints used by Bitwave's Close
Dashboard. It is an interface, not a close-policy engine: it returns Bitwave
state and performs explicit operations, while Wavie or the operator decides
task order, evaluates evidence, chooses accounting treatment, and decides
whether an exception should be accepted.

Every read emits JSON. Every mutation requires `--yes` and supports
`--dry-run`. Commands use the active organization unless `--org` is supplied.

## Mental model

- A **template** defines the available close tasks and dependencies.
- A **run** applies a template to one close period.
- A **task** runs a Bitwave check or action and records status, alerts, evidence,
  dependencies, and output.
- An **invocation** is asynchronous backend execution started by a task.
- A **certification** summarizes the completed run and links its check reports.
- **Artifacts** are the reports generated by individual tasks.
- **Delivery paths** assign generated reports to configured SFTP destinations.

The CLI does not automatically accept warnings, complete runs, or hard-close a
period. Read the returned task/run state after each asynchronous operation.

## Checklist runs

| Command | Endpoint | What it does |
|---|---|---|
| `close list` | `GET /v3/orgs/{org}/checklists` | Lists periods; filters by template/start/end date. |
| `close get RUN_ID` | `GET /v3/orgs/{org}/checklists/{run}` | Returns run progress plus task state. |
| `close create -i run.json --yes` | `POST /v3/orgs/{org}/checklists` | Creates a run. Use `version: 2`. |
| `close update RUN_ID -i patch.json --etag ETAG --yes` | `PATCH …/{run}` | Updates stored run parameters/template; does not run tasks. |
| `close run RUN_ID --yes` | `POST …/{run}/run` | Starts all runnable tasks or a `--task` subset. |
| `close complete RUN_ID -i complete.json --etag ETAG --yes` | `PATCH …/{run}/complete` | Completes a run using optimistic concurrency. |
| `close delete RUN_ID --yes` | `DELETE …/{run}` | Deletes a run. |
| `close hard-close --end-date DATE --yes` | `updateOrg` GraphQL mutation | Sets the organization hard-close date. |

Typical create body:

```json
{
  "parameters": {
    "templateId": "close_period",
    "startDate": "2026-07-01",
    "endDate": "2026-07-31"
  },
  "version": 2
}
```

Template parameters vary. Inspect the selected template instead of inventing
IDs or configuration values.

## Tasks and invocations

| Command | Purpose |
|---|---|
| `close task list RUN_ID` | List tasks in the run. |
| `close task get RUN_ID TASK_ID` | Read one task's dependencies, evidence, alerts, and output. |
| `close task run RUN_ID TASK_ID --yes` | Start/retry one task. Optional JSON carries task-specific overrides. |
| `close task update RUN_ID TASK_ID -i patch.json --etag ETAG --yes` | Apply the backend task patch contract. |
| `close task accept RUN_ID TASK_ID --reason TEXT --yes` | Record human acceptance of a needs-review result. |
| `close task unaccept RUN_ID TASK_ID --yes` | Reverse a prior acceptance. |
| `close invocation get INVOCATION_ID` | Poll asynchronous task execution and read output. |

Starting a task acknowledges execution; it does not mean the check passed.
Status values and dependency blocks must be read from the server response.

## Templates

`close template list`, `catalog`, and `get` expose available templates and task
types. `create`, `update`, and `delete` accept the same JSON used by the template
designer. Updates/deletes accept `--etag` and send `If-Match`.

Built-in templates may be read-only. The CLI does not select a template merely
because it exists; the caller must use the intended template ID.

## Certifications and artifacts

| Command | Purpose |
|---|---|
| `close certification list` | List generated close certifications with cursor pagination. |
| `close certification create -i body.json --yes` | Generate one for `checkListRunId`. |
| `close certification get REPORT_ID` | Read overall status and individual checks. |
| `close certification status REPORT_RUN_ID` | Poll certification generation. |
| `close certification download-link REPORT_ID` | Get the signed PDF URL. |
| `close artifact get REPORT_RUN_ID` | Read a generated task report record. |
| `close artifact download-link REPORT_RUN_ID` | Include generated report download URLs. |
| `close artifact snapshot REPORT_ID` | Read the snapshot used by close delivery. |

## Supporting close data

- `close inventory-actions VIEW_ID --as-of DATE` exposes the inventory actions
  used by close checks and can request exported results.
- `close export EXPORT_ID` retrieves those asynchronous export results.
- `close rollup-config list|get` exposes the rolled-up JE configurations that
  close templates can reference.
- Existing `bitwave inventory` commands list and run inventory views.
- Existing `bitwave accounting connections list` exposes accounting
  connections selectable by close tasks.
- Existing `bitwave report balance`, `report transaction-export`, and
  `report actions` commands produce their corresponding organization reports.
- Existing `bitwave transaction review summary` exposes evidence-oriented
  transaction counts (categorized, uncategorized, ignored, pricing and sync
  states) without recommending accounting decisions.

## SFTP delivery

`close delivery path` lists, tests, creates, updates, and deletes reusable SFTP
paths. `close delivery assignment` lists or changes the report-to-path mapping
for a checklist run. The assignment API stores destination selection; starting
the relevant close task performs delivery.

Use `--dry-run` before any delivery mutation. Connection credentials remain in
Bitwave; the CLI accepts Bitwave connection/path identifiers, not remote
credentials.
